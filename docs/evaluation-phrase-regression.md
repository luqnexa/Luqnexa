# 評価表現と「こんな感じ」の誤変換修正

2026-10-12、ユーザーの「結構精度害意よ」「こんな漢字で精度が悪い」という報告を調査した。Mozc由来のローカル辞書を使うCLIで、修正前の先頭候補が `精度害意よ`、`こんな漢字` となることを再現した。

短い分割を優先するトークンコストにより `が＋いい` が `害意` に負けていた。`が/は` と `いい/よい/わるい` の組み合わせを、辞書にある述語表記から文法表現として生成し、局所的な順位加点を行った。文章内の終助詞 `よ/ね/ぞ` が同音の名詞へ変わる候補も抑制した。

`こんな/そんな/あんな/どんな` の後の `感じ` に小さな順位加点を追加した。`漢字` は妥当な場合があるため削除しない。単独の `かんじ` の先頭候補は従来どおり `漢字`。単独の `がいい` から `害意` を選ぶ変換も保持する。

これは明示的な局所ルールによる改善であり、文章全体を理解するニューラルAIを新しく学習した変更ではない。青空文庫の学習成果物や個人履歴は使用・適用していない。

## 確認結果

修正後、ローカルの `dictionaries/mozc-ja.tsv` を指定したCLIの先頭候補は次のとおり。

| 読み | 先頭候補 |
| --- | --- |
| せいどがいいよ | 精度がいいよ |
| こんなかんじ | こんな感じ |
| こんなかんじでせいどがわるい | こんな感じで精度が悪い |

再現コマンド: `cargo run -p nextime-cli --release -- --dictionary dictionaries/mozc-ja.tsv --limit 8` に各読みを標準入力で渡す。

変換クレートに2件の回帰テストを追加し、複数の主語・終助詞、同音語の保持、4種の指示表現を検証した。fmt、clippy（警告をエラー扱い）、ワークスペーステスト、releaseビルドは成功した。Windowsリンカーのライブラリ生成案内がビルドログに出るが、ビルド終了コードは0。

現在の端末内AIによる再ランキングを含む実際のアプリ操作は、このCLI検証では測定していない。修正ソースとビルド成果物を用意した段階では、既存の登録済みIME DLLには反映されない。稼働中アプリへの反映にはIME更新とアプリの再起動が必要。

## 「したい」の分割防止（2026-10-12）

画像の「あなるセックスしたい」を既存NUDで再現すると、「あなるセックスした位」が先頭になった。サ変接続する名詞の後で、認識済みの「したい」より短い「した」を選び、残りの「い」を位・医・胃などへ変換する経路が原因だった。

「したい」「したいです」「したかった」「したくない」「したくないです」「したくなかった」「したくて」を文法表へ追加。サ変接続の許される位置では最長の認識済み活用を保持し、その開始位置で短い活用や同音名詞へ分割しない。独立した「したい→死体」や「い→胃」の辞書候補は保持する。一般名詞同士の自由な連結は許可しない。画像の複合語を手書きの辞書オーバーレイに登録し、セックス・勉強・検索のサ変接続品詞も明示した。NUD全体の再構築は不要。

既存約128万エントリNUDを指定した修正CLIで、先頭候補は「アナルセックスしたい」「セックスしたい」「勉強したい」「検索したいです」。画像の入力では複合語＋活用と読みのフォールバックの2候補になり、「した位」や「アナる」等を出さないことを確認した。

変換クレートは10テスト成功。2種類の名詞×7活用と単独同音語を検証し、Rustセッションでは5入力×AI有効・無効の10ケースを一文字ずつ入力し、Spaceで候補表示、Enterだけで確定することを検証した。既存NUDを使用するPowerShell文脈回帰にも同じ5入力を追加し、固有名詞・文脈・個人学習・文章学習の既存回帰とともに成功。workspace test、clippy、fmt、Windows releaseビルド、設定6ケース、TSF統合テストが成功した。

ホスト計測1000回・warmup100はp50=3.2528ms、p95=5.0275ms、最大34.3974ms。この回は5ms目標をわずかに超えた。描画・LLM推論なしの開発端末で、負荷の原因は未切り分け。iPhone SE・1億エントリの達成値ではない。これは文法と語彙の修正でありニューラルAIの追加学習ではない。「設定ファイルが見つかりません」は別の未解決問題で、診断コードを用意済み。前回のUACキャンセルのため、今回のビルドも稼働中IMEへはまだ適用していない。

その後、ユーザーから更新再実行の明示許可を受け、Windows UACによる更新が成功した。登録先は `C:/Program Files/NextIME/build-5280620c970409b7/nextime_tsf.dll`。登録と12ファイルのSHA-256、登録済みTSFのOS有効化と統合テストが成功。インストール済みFFIと既存NUDを直接使用し、画像の入力・勉強したい・検索したいですを一文字ずつ入力して、期待する表示と自動確定なしを検証した。登録確認付きホスト計測はp50=4.2557ms、p95=5.6925ms、最大20.8028msで、この回も5ms目標未達。実アプリへの反映は入力先の完全終了・再起動が必要で、AI設定未検出の原因は診断結果待ち。

## 愛とAIの候補保持（2026-10-12）

「あいをつかめ」がAIをつかめ等だけになる原因は、粒子付き「あいを→AIを」の完全一致辞書で愛の分割経路を押し出していたこと。読み「あいを」に同じ重みの「愛を」を追加し、「あいをたしかめたい」「あいをたしかめる」もAIと愛の両方を辞書に保持した。「つかめ」の動詞候補を登録し、愛を＋掴め／つかめに限定した局所的な接続優先を追加。AIの候補は削除しない。

既存の文脈ヒントへAI／愛の同音語組と人工知能・機械学習・ChatGPT、恋人・恋愛・愛情等の手書きヒントを追加した。これらはニューラルAIの学習ではなく、既存候補の順位調整。合成文脈テストで「恋人への愛情」では愛を確かめたい、「人工知能の動作」ではAIを確かめたいが先頭になることを検証。文脈なしでは両候補の保持を検証し、AIだけを強制する旧回帰の期待値を修正した。

既存約128万語NUDのCLIでは愛を掴めが先頭、AI有効のセッションでは愛をつかめが先頭で、どちらも愛を掴めとAIを掴めを含む。fmt、clippy、workspace test、Windows設定6ケース・TSF統合、固有名詞・文脈・個人学習・文章学習の回帰が成功。ホスト計測p50=2.8652ms、p95=4.2747ms、最大16.9239ms（1000回、warmup100、描画・LLMなし、開発機）。ニューラルモデルの実推論や一般的な変換精度の達成値ではない。
