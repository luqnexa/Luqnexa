# Luqnexa Phase 1 設計

この文書はPhase 1時点の設計記録です。現在のディスク辞書・共通検索インターフェース・NEXC実装は [Phase 2仕様](nexc-format.md) を参照してください。

## 境界とデータフロー

今回の完成範囲は日本語の通常変換を行う同期Rustコアです。I/OはCLIに限定し、コアにOS API、ネットワーク、永続的な学習、AIを持ち込みません。

```text
入力（ローマ字 / ひらがな / 全角カタカナ）
  → Engine: 生入力のバイト数制限
  → Parser: 正規化済みの読み
  → Convert: UTF-8文字境界の候補ラティス
      → Dictionary: 各部分文字列を二分探索
      → Ranker: 頻度スコア・同表記の重複排除・beam制限
  → Conversion { reading, candidates }
  → CLI: ユーザーに表示
```

`Engine` は不変の辞書を所有します。変換ごとの状態はローカルに生成し、入力や候補をディスクに残しません。別スレッドでも共有できます。アプリへの文章挿入やメッセージ送信の機能はありません。

## 入力解析

ASCII英字を小文字化し、全角カタカナU+30A1〜U+30F6をひらがなへ写像します。ローマ字テーブルの最長一致で読みを生成します。同一子音の反復と `tch` を促音として扱い、`n` / `nn` / `n'` に専用規則を適用します。カンマ・ピリオドは読点・句点、ハイフンは長音記号になります。

未知文字は保持しますが、英字大小や句読点は上記の正規化対象です。半角カナ、結合濁点、Unicode NFC、すべてのローマ字入力方式には未対応です。未確定の子音 `k` や `ny` は保持し、末尾の `n` は `ん` に確定します。キーイベントごとの未確定文字列（preedit）管理はPhase 3で別APIとして追加します。

現在は各位置で小さな静的テーブルを走査します。将来は計測に基づきfirst-byte indexやtrieを検討します。

## 辞書

`Entry` は読み・表記・品詞・u32頻度を所有します。読みの昇順、頻度の降順、表記・品詞の順に並べ、二つの `partition_point` で完全一致の連続スライスを返します。検索時の辞書エントリコピーは不要です。

- 構築: ソートを含めO(N log N)、全体をRAM上に保持。
- 完全一致検索: O(log N)、返却値は借用スライス。
- 変換時: 各スライスの先頭から最大候補数までのエントリを使用。

同じ表記に異なる品詞が多数ある場合、辞書エントリの打ち切りにより異なる表記の候補数が少なくなることがあります。Phase 2以降で検索インデックスと品詞別の文脈スコアを設計する必要があります。

サンプル辞書はBase Dictionaryに相当する最小デモです。Dynamic / Personal Dictionary、追記・暗号化・学習は未実装です。

## 候補生成

読みをUnicodeスカラー値の境界で区切ります。各始点から辞書の最大読み長まで完全一致検索し、辞書語を辺として扱います。各文字のliteral辺も追加するので未知の絵文字や漢字があっても変換を続行できます。

各位置で上位K候補だけ保持するbeam searchです。候補は表記、i64スコア、分割数を持ちます。中間候補は各辺追加後に枝刈りし、一時的には最大K + K²候補となります。語の表記は最大256文字、入力は最大128文字、Kは最大32です。極端な表記長・同音異義語の辞書ではメモリとCPUの追加測定が必要です。

候補数2以上では読みそのものを候補に残し、必要なら末尾候補を置き換えます。候補数1では最良候補を返します。これは近似探索であり、すべての組合せや厳密なN-bestを保証しません。活用・接続品詞・文節境界を学習する形態素解析はまだありません。

## ランキング

頻度fの単語スコアは、256倍の `log2(f + 1)` を区間内の整数線形補間で近似し、8448を減算します。語スコアは常に負で、無意味な細分割を抑えます。literal辺は1文字あたり-12288です。パス上のスコアを加算し、スコアの降順、分割数の昇順、表記の辞書順で順位を決めます。同じ表記は最良パスにまとめます。

スコアは確率や信頼度ではありません。頻度の量子化で同点になる場合があります。コーパス、文脈、ユーザー学習を用いて最適化したランキングではありません。

## 性能と測定

ベンチマークは `Engine::convert` の開始から返却までを測定します。入力解析・辞書検索・候補生成・順位付けを含め、辞書ロード、入力生成、描画、出力を除きます。warmup後の呼び出しを個別に計測し、nearest-rankのp50/p95/p99と最大・平均値を出力します。初期化時間は別計測です。

現在はユーザーレベルの候補キャッシュやファイルI/Oを使用しません。辞書ヒット・ミスはキャッシュヒット・ミスと同義ではありません。CPUキャッシュやOSスケジューラの影響を制御していません。1億語、iPhone SE、低電力・発熱・省電力・消費電力、他IMEとの同条件比較は未実施です。

## 今後のフェーズ

1. **Phase 2:** NEXC-Core / Lite / Max、可逆 `.nud`、読み・表記・品詞・頻度の往復検証、追記辞書、圧縮状態の検索、破損データ検証、1億語の再現可能な測定。既存圧縮ライブラリをNEXCの内部エンジンに使用しません。圧縮率と検索速度の両方を測定します。
2. **Phase 3:** ABIを固定したFFI、Windows TSF、Linux IBus/Fcitx5、macOS InputMethodKit、キーイベントとpreedit、候補UI、インストール・アンインストール、各OSの統合テスト。
3. **Phase 4:** Axum/Tokio API、PostgreSQL、Redis Streams、R2、認証・検証・レート制限・監査、公開情報の新語審査、署名付きManifest、SHA-256/Ed25519、差分・原子的切り替え・ロールバック。公開データの利用条件も確認します。
4. **Phase 5:** 明示同意を通したローカルAI、複数下書き、ユーザー操作で挿入・送信。Memoryは初期無効、ローカル暗号化、相手別管理、保持期限、確認・訂正・削除、公式連携。共有許可された単語以外の入力全文や個人会話を自動送信しません。
5. **Phase 6:** Android InputMethodService / iOS Custom Keyboard Extension、全OS実機検証。iOSのサンドボックス・メモリ・バックグラウンド制限を守り、会話取得はユーザーの共有操作や公式APIを使います。全端末が同じフル辞書を保持する方針で、AdaptiveはAIモデル・キャッシュだけを調整します。

各フェーズは実測と動作検証を完了してから実装済みと扱います。現在、NEXCの圧縮性能やAI精度について実績値はありません。
